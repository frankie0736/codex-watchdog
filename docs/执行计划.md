# Codex Watchdog 执行计划

> 基于 [`需求与调研记录.md`](需求与调研记录.md)，并用本机数据做了只读核实（2026-10-12，codex-cli 0.162.0，Go 1.26.2）。

## 0. 先修正需求文档里的几个判断

我只读查询了 `~/.codex` 的数据库，下面几条和需求文档的假设对不上，计划会按这些事实调整：

| # | 文档假设 | 实测 | 影响 |
|---|---|---|---|
| F1 | 最新 turn 为 `inProgress` 就说明会话在运行 | 74 个 `inProgress` turn 里有 **73 个超过 1 天**，基本都是进程崩溃或被关掉后留下的僵尸 turn | 验收标准 #1 照原样做会列出几十个假活跃会话。"运行中"必须同时满足新鲜度条件（例如 `started_at` 在 N 小时内），否则标成 `ORPHANED` |
| F2 | `codex queue` 成功就等于消息送达 | `queue_1.sqlite` 里有 2 条 **2026-09-02 入队、到现在都没被消费**的消息，对应 thread 之后也没有新 turn | queue 只是持久化入队，**能不能被消费要看是否有 app-server/客户端挂着这个 thread**。这是整个项目的核心未验证假设，必须先做 spike |
| F3 | 一个 home 对应一个 app-server | 本机同时跑着：ChatGPT App 自带的 app-server（3 个）、VS Code 内嵌的 codex、`~/.codex` 和 `~/.codex-sub` 各一个 daemon | `codex queue` 默认连哪个 server、能不能唤醒 ChatGPT App 里加载的 thread，都需要实测 |
| F4 | `originator` 可以用来识别来源 | 大部分 thread 的 `originator` 是空的，`source` 才是稳定字段（`cli`/`vscode`/`exec`/subagent JSON） | 来源识别和白名单以 `source` 为主，`originator` 作为补充 |
| F5 | — | 全部历史里最新 turn 是容量错误的 thread 有 72 个，其中 70 个超过 1 天 | 必须有新鲜度窗口，否则首次启动就会把几十个旧会话一起唤醒 |

另外确认过的事实：`codexErrorInfo = "serverOverloaded"` 一共 605 条，和 "at capacity" 文本匹配的数量**完全一致**，所以检测器以 `codexErrorInfo` 为主键、文本匹配兜底即可。`rollout_ordinal` 在同一 thread 内没有重复值，可以用来稳定地确定"最新 turn"。`429 responseTooManyFailedAttempts` 属于另一类错误，第一版**不处理**。

## 1. 已确认的决策（来自本次访谈）

- 主要场景：**Codex CLI TUI** 和 **ChatGPT App 的 Codex**。spike 只测这两种。
- Codex home：自动发现 `~/.codex*` 目录下含 `state_5.sqlite` 的 home，`~/.codex` 和 `~/.codex-sub` 都监控；每个 thread 绑定自己的 home。
- queue 之后没有出现新 turn：**在限流范围内重试**。我额外加了上限 `max_retries_per_turn`（默认 3），到上限后标成 `NEEDS_ATTENTION` 并停止。理由是 F2：消息没被消费时，每次重试都会在队列里再叠一条"继续"，客户端重新连上时会连续收到多条。
- 范围：只处理交互式会话，排除 `exec` 和 subagent thread。

## 2. 阶段划分

### Phase 0 — Spike：验证 `codex queue` 能不能真的唤醒会话（不写 Go）

这是整个项目的前提。如果答案是"不能"，后面的架构都要改，比如改成直接连 app-server 的 WebSocket 发 `turn/start`。

步骤（每一步都要人在场，用一次性会话）：

1. **CLI TUI**：`codex` 开一个新会话，跑一个短 turn 后保持 TUI 打开。在另一个终端执行 `codex queue --thread <id> --message "ping"`，观察：
   - `queue_1.sqlite` 里是否出现 item、多久后被删掉
   - `thread_turns` 是否出现新 turn
   - TUI 界面上能不能看到
2. **CLI TUI 已退出**：同一个 thread 退出 TUI 后再 queue 一次。预期消息会滞留，用来确认 F2 的机制。
3. **ChatGPT App Codex**：对 App 里的一次性 thread 做同样的测试，同时记下 `codex queue` 实际连上了哪个 server。可以用 `lsof -p` 或 `--remote` 的行为差异来判断。
4. **`~/.codex-sub`**：用 `CODEX_HOME=~/.codex-sub codex queue ...` 验证 home 路由。
5. **failed 状态**：最难自然复现。可以先等一次真实的容量错误再做第 1 步；如果拿不到，就用 interrupted turn 作为近似，并在报告里写明这个差异。

产出：`spike/RESULT.md`，写清楚每种客户端 × 是否在线 → 消息是否送达、延迟多少、留下了什么痕迹。并且明确判断：**用 queue_1 里的消息是否已被消费，还是用 thread_turns 里是否出现新 turn，作为"送达"的判定信号。**

退出条件：至少 CLI TUI 在线场景确认能送达。否则停下来重新设计。

### Phase 1 — 只读监控（不发送）

目标：TUI 能正确列出会话和容量错误候选，**零写入**。

- `config`：TOML 配置加载和校验（字段见需求文档 §7，另加 `active_max_age_seconds`、`max_retries_per_turn`、`allowed_sources`、`delivery_timeout_seconds`）。缺省值就是安全值，非法配置直接 fail fast。
- `home`：自动发现 `~/.codex*`，检查三个数据库文件是否存在。
- `store`：使用 `modernc.org/sqlite`（纯 Go，不依赖 cgo），以 `mode=ro` 打开，**不用 `immutable=1`**（否则看不到 WAL 里的新数据），并设置 `busy_timeout`。
  - 每次轮询的查询：`thread_history_1` 用窗口函数取每个 thread 最新的 turn，并只取 `started_at`/`completed_at` 在窗口内的；`state_5.threads` 按 id 批量取元数据。两个库**分开查、在 Go 里 join**（`ATTACH` 只读库在 WAL 下容易踩坑）。
  - 启动时检查 schema：所需列不存在就把对应 home 标成 `SCHEMA_INCOMPATIBLE`，界面显示出来，不 panic。
- `detector`：纯函数 `(turn, thread, now, cfg) -> Classification`，输出 `ACTIVE / ORPHANED / CAPACITY_CANDIDATE / STALE / OTHER_ERROR / IDLE / EXCLUDED`。
- `tui`：bubbletea + bubbles/table + lipgloss，包含顶部状态栏、会话表、详情页，以及 `q/r/Enter` 三个键。
- 日志：用 `slog` JSON 格式写到 `~/.local/state/codex-watchdog/watchdog.log`，每次运行生成一个 `run_id`。

验收：拿真实数据库跑，F1 里那 73 个僵尸 turn 必须显示为 `ORPHANED` 而不是 `ACTIVE`；最近 1 小时内的那个容量错误必须显示为候选。

### Phase 2 — 决策引擎 + 持久化状态（dry-run）

- `state`：自己的 SQLite（`~/.local/state/codex-watchdog/state.db`），**和 Codex 的数据库完全隔离**。
  - `attempts(home, thread_id, failed_turn_id, attempt_no, decided_at, executed_at, result, exit_code, stderr_summary, dry_run)`
  - 主键 `(home, thread_id, failed_turn_id, attempt_no)`
- `limiter`：纯函数决策，按需求文档 §7 的 7 步顺序判断，每一步都返回**拒绝原因**（TUI 里显示为"等待 grace 剩 12s"这类提示）。全局限流用持久化的滑动窗口，从 attempts 表按时间算，不维护内存桶，这样重启后状态仍然正确。
  - 重试规则：attempt N 之后如果 `delivery_timeout_seconds` 内没有出现新 turn，且 N < `max_retries_per_turn`，且满足 cooldown，就允许 attempt N+1。
  - **先写 attempt 记录（状态 pending），再执行 queue**。这样崩溃后宁可少发也不会重复发。
- `watcher`：ticker 驱动 `poll → classify → decide → (execute)`，全程传递 context，支持优雅退出。
- 默认 `dry_run = true`，TUI 上明确显示 `DRY-RUN`。
- 键位：`p` 暂停，`d` 切换 dry-run，`l` 查看日志。

验收（全部用单元测试驱动，用表格测试覆盖）：
- 同一个 failed turn 连续轮询 100 次只产生 1 次决策
- 重启后 cooldown 和全局窗口仍然生效
- 首次启动时窗口外的旧错误不触发
- 第 `max_retries+1` 次被拒绝，并进入 `NEEDS_ATTENTION`

### Phase 3 — 真实发送

- `queue`：`exec.CommandContext("codex", "queue", "--thread", id, "--message", msg)`，用参数数组调用，不经过 shell；环境变量设置 `CODEX_HOME=<该 thread 所属 home>`；30s 超时；记录 stdout/stderr 摘要（截断，不含会话正文）。
- 按 Phase 0 的结论实现"送达确认"：等到新 turn 出现后标记 `RECOVERED`，超时则进入重试判断。
- 状态机：`CAPACITY_DETECTED → WAITING_RATE_LIMIT → QUEUEING → QUEUED → RECOVERED | QUEUE_FAILED → (retry) | NEEDS_ATTENTION`
- 每次真实发送都写一条结构化日志：`run_id, home, thread_id, turn_id, attempt, result, latency`。

验收：在一次性 CLI 会话上做端到端测试，把一个 interrupted/failed turn 作为候选，确认自动发送、恢复和去重都正确。

### Phase 4 — 打磨（按需）

- `s` 设置面板（只改运行时配置，不回写文件，YAGNI）
- macOS 通知：只在 `NEEDS_ATTENTION` 时触发（`osascript`，零依赖）
- 进程/daemon 校验，降低误判 `ORPHANED` 的概率

## 3. 项目结构

```
cmd/codex-watchdog/main.go
internal/config     配置 + 校验
internal/home       多 home 发现
internal/store      只读 SQLite 查询（Codex 库）
internal/detector   分类（纯函数）
internal/limiter    决策（纯函数，注入 now）
internal/state      自有状态库
internal/queue      codex queue 执行器（接口，便于测试时替换）
internal/watcher    轮询编排
internal/tui        bubbletea 视图
testdata/           构造的 fixture sqlite（不提交真实库）
```

测试重点放在边界上：`store` 用 fixture 数据库做测试（包括 WAL 模式下另一个连接正在写入的情况）；`detector` 和 `limiter` 用表格测试；`queue` 通过接口 mock，再写一个用假 `codex` 脚本放在 PATH 前面的集成测试，校验参数和 `CODEX_HOME`。

## 4. 风险

| 风险 | 缓解 |
|---|---|
| `codex queue` 对离线 thread 不生效（F2） | Phase 0 先验证；重试有上限；`NEEDS_ATTENTION` 提示人工处理 |
| 重试导致同一个 thread 积压多条"继续" | 每次重试前读 `queue_1.sqlite`，**该 thread 还有未消费的 item 就不再追加** |
| Codex 升级后 schema 或文件名变化（`state_5`→`state_6`） | 按 glob 发现最高版本号的文件 + 启动时做 schema 检查，失败就显示出来，不自动适配 |
| 容量错误持续存在，"继续"只会再次失败 | 本来就有 cooldown 和全局限流；后续可以考虑指数退避，第一版不做 |
| 误唤醒用户自己故意停下的会话 | 只处理 `serverOverloaded`；`interrupted` 永远不处理 |

## 5. 仍待确认（不阻塞 Phase 0/1）

- 新鲜度窗口：30 分钟还是 1 小时？我的倾向：错误窗口 1 小时，"活跃 turn"窗口 6 小时。
- 全局每分钟 5 次 / 单会话 cooldown 5 分钟：先按这个默认值，Phase 3 实际跑过之后再调。
