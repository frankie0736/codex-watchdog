# Codex 会话看护 TUI：需求与调研记录

> 状态：历史文档，记录立项时的需求与调研；实现以代码和 README 为准。  
> 调研环境：macOS，Codex CLI `0.162.0`；本机 app-server daemon 可见版本为 `0.162.1`。

## 1. 目标

制作一个用 Go 编写的长期运行 TUI。用户只需要启动并保持这个 TUI 打开，它就持续完成两件事：

1. 展示当前活跃的 Codex 会话及其状态。
2. 发现会话因为模型容量不足而卡住时，按照频率限制，自动向该会话发送：`继续`。

这个工具的目的不是删除、关闭或强制终止会话，而是帮助仍然存在的会话从容量错误状态继续运行。

## 2. 已确认的用户需求

### 2.1 TUI

- 使用 Go 实现。
- 是一个持续运行的终端界面，而不是执行一次后退出的命令。
- 启动后持续刷新会话列表。
- 能看到所有需要监控的活跃会话，而不是只看当前工作目录。
- 能看到会话的基本状态、最近一次活动、最近错误和自动处理次数。
- TUI 关闭时不应改变 Codex 会话本身；关闭只停止监控和自动发送。

### 2.2 自动恢复

- 识别错误：`Selected model is at capacity. Please try a different model.`
- 识别到目标会话卡住后，执行等价操作：

  ```bash
  codex queue --thread <THREAD_ID> --message "继续"
  ```

- 自动发送必须针对具体 thread/session ID。
- 发送成功后，在界面中留下可见记录。
- 不能因为 TUI 刷新或数据库轮询重复发送同一个恢复消息。
- 如果发送失败，需要显示失败原因，并按重试策略处理，而不是静默丢失。

### 2.3 频率控制

用户明确要求不能“错误一出现就发一次”，需要可配置的最高频率限制。至少需要以下两层限制：

- 全局限制：所有会话合计每分钟最多发送多少次。
- 单会话限制：同一个会话两次自动发送之间至少间隔多久。

建议额外支持：

- 首次发现错误后的延迟（例如错误持续 30 秒后才处理）。
- 同一个失败 turn 只处理一次。
- `codex queue` 执行失败后的重试间隔。
- 启动时是否处理启动前已经存在的最近错误。
- dry-run/暂停自动发送模式。

## 3. 本机调研结果

### 3.1 CLI 已有命令

本机 `codex --help` 显示：

- `codex agents`：浏览共享本地 app-server daemon 上的 Agent 会话。它是交互式总览界面，不是 JSON/纯文本列表接口。
- `codex resume --all --include-non-interactive`：浏览已保存会话，偏向历史/可恢复会话，不等同于“当前仍活跃”。
- `codex queue --thread <THREAD> --message <TEXT>`：向已有会话排队发送消息，是自动发送“继续”的现成入口。

`codex agents` 依赖共享 app-server；使用 `--no-daemon` 启动的会话可能不会出现在该总览中。因此 TUI 不能只依赖 `codex agents` 的屏幕输出，需要直接读取本地状态，必要时再结合进程/daemon 信息。

### 3.2 本地 SQLite 状态

本机默认 Codex 数据目录为 `~/.codex`，发现的关键数据库：

- `~/.codex/thread_history_1.sqlite`
- `~/.codex/logs_2.sqlite`

数据库可能使用 WAL 文件（例如 `-wal`、`-shm`），读取程序必须以只读方式打开，并允许 WAL 读取；不能复制或修改数据库文件。

`thread_history_1.sqlite` 中的关键表：

- `thread_turns`：每个 thread 的 turn、状态、开始/完成时间、错误 JSON。
- `thread_items`：会话中的用户消息、Agent 消息、命令执行等项目，可用于取得标题/最近活动摘要。

`thread_turns.status` 实际出现过：

- `inProgress`
- `completed`
- `failed`
- `interrupted`

时间字段 `started_at`/`completed_at` 是 Unix 秒时间戳，不是毫秒。

### 3.3 容量错误的实际数据形态

`thread_turns.error_json` 中实际看到的形式类似：

```json
{
  "message": "Selected model is at capacity. Please try a different model.",
  "codexErrorInfo": "serverOverloaded",
  "additionalDetails": null,
  "misalignment": null
}
```

因此检测器应优先解析 JSON 的 `message` 和 `codexErrorInfo`，同时保留对原始文本的大小写不敏感匹配，以兼容未来格式变化。

当前本机数据库还观察到大量 `failed` turn 和 `inProgress` turn，说明仅查看操作系统里的 Codex 进程不足以判断某个 thread 的业务状态；应以 thread/turn 状态为主。

### 3.4 多个 Codex 数据目录

本机同时存在 `~/.codex` 和 `~/.codex-sub` 相关运行痕迹。未来 TUI 应支持配置多个 Codex home/database；发送 queue 时要使用产生该会话的对应 `CODEX_HOME`，避免把消息发到错误的 daemon/会话存储。

默认可以只监控 `~/.codex`，但界面和配置中必须明确当前监控的数据库来源。

## 4. “活跃会话”的定义

需要区分三个概念：

1. **运行中的 turn**：最新 turn 状态为 `inProgress`。
2. **仍可被继续的会话**：会话没有被删除/归档，且 app-server 或对应 CLI 仍可接受 queue 消息。
3. **历史保存会话**：可以通过 `codex resume` 找到，但当前不一定运行。

第一版建议采用以下可解释规则：

- 列表中的“运行中”以某 thread 最新 turn 为 `inProgress` 判定。
- 最新 turn 为 `failed` 且错误属于容量错误时，标记为“待自动恢复候选”；只处理最近配置窗口内的错误。
- `completed`、`interrupted` 或其他错误默认不自动发送“继续”。
- 对于最新容量错误很久以前发生的历史会话，不自动唤醒，避免 TUI 首次启动时误恢复大量旧会话。
- 是否将“最新 turn 为容量错误”视为活跃，必须通过可配置的错误新鲜度窗口控制；默认建议 30 分钟或 1 小时。

这是基于本地持久化状态的“可监控活跃”，不是对所有终端窗口的绝对进程级证明。后续可以加进程/daemon 校验，进一步降低误处理概率。

## 5. 建议的状态机

每个 thread 在 TUI 中显示一个状态：

```text
UNKNOWN
  -> ACTIVE              最新 turn = inProgress
  -> CAPACITY_DETECTED   最新 turn = failed 且匹配容量错误
  -> WAITING_RATE_LIMIT  已发现错误但尚未达到发送条件
  -> QUEUEING            正在执行 codex queue
  -> QUEUED              queue 成功，等待新 turn 出现
  -> RECOVERED            后续出现新的 inProgress/completed turn
  -> QUEUE_FAILED         queue 失败，等待重试
  -> STALE                错误超过新鲜度窗口
```

关键去重键建议是 `(database/home, thread_id, failed_turn_id)`。同一个失败 turn 无论 TUI 刷新多少次，都只允许触发一次自动 queue；只有出现新的失败 turn，才产生新的自动恢复机会。

## 6. 建议的 TUI 内容

### 6.1 顶部状态栏

- 监控中的数据库/home 数量。
- 活跃会话数量。
- 容量错误候选数量。
- 等待频率限制数量。
- 本次运行已发送次数。
- 最近一次轮询时间。
- 自动发送开关：`ON`/`PAUSED`。

### 6.2 会话表

建议列：

| 列 | 含义 |
|---|---|
| 状态 | ACTIVE、容量错误、等待限流、已发送、失败等 |
| Thread ID | Codex thread ID，可复制 |
| 最近 turn | 最近 turn ID |
| 最近活动 | 本地时间 |
| 错误 | 错误摘要 |
| 最近自动发送 | 时间、结果 |
| 发送次数 | 当前运行/持久化累计次数 |
| 来源 | `~/.codex` 或其他 home |

### 6.3 交互建议

- `q`：退出 TUI，不终止 Codex。
- `p`：暂停/恢复自动发送。
- `r`：立即刷新。
- `Enter`：查看选中会话详情和最近错误。
- `s`：查看/临时修改限流配置。
- `d`：切换 dry-run（只显示将发送什么，不真正执行）。
- `l`：查看自动处理日志。

## 7. 建议的限流模型

默认值只是建议，最终应放到配置文件和 TUI 设置中：

```toml
poll_interval_seconds = 5
capacity_error_grace_seconds = 30
capacity_error_max_age_seconds = 3600
global_max_sends_per_minute = 5
per_thread_cooldown_seconds = 300
queue_retry_seconds = 120
startup_recover_recent_errors = true
dry_run = false
message = "继续"

[[codex_home]]
path = "~/.codex"

# 如需监控第二套本地 Codex 状态，再显式添加：
# [[codex_home]]
# path = "~/.codex-sub"
```

限流决策顺序建议为：

1. 错误是否匹配容量错误。
2. 是否仍在错误新鲜度窗口内。
3. 该失败 turn 是否已经处理过。
4. 是否满足错误 grace period。
5. 是否满足单 thread cooldown。
6. 是否超过全局每分钟上限。
7. 满足后才执行 `codex queue`。

全局频率限制建议使用令牌桶或滑动窗口；单 thread 使用持久化的 `last_queued_at`。这样即使 TUI 重启，也不会立刻重复轰炸同一个会话。

## 8. 建议的 Go 结构

暂不实现，但实现时可以拆成以下组件：

- `store`：只读 SQLite 连接、WAL 读取、查询最新 turn 和最近错误。
- `detector`：把数据库记录归类为 active/capacity/stale 等状态。
- `limiter`：全局滑动窗口、单 thread cooldown、失败 turn 去重。
- `queue`：为指定 Codex home 执行 `codex queue`，捕获退出码、stdout、stderr。
- `state`：保存自动发送记录、去重键、重试时间和运行配置。
- `watcher`：定时轮询、取消、优雅退出。
- `tui`：表格、详情、键盘操作和状态提示。

所有组件都应支持 context cancellation；退出时关闭 SQLite 连接、停止子进程、保存状态。

## 9. 失败和安全边界

- SQLite 只读；不直接更新 Codex 数据库。
- 不自动执行 `archive`、`delete`、`kill` 或 `restart`。
- 不把完整会话正文写入日志，默认只记录 thread ID、turn ID、错误摘要和结果。
- `codex queue` 的命令参数必须使用参数数组调用，不能通过 shell 拼接，避免 thread/message 内容造成命令注入。
- 如果数据库锁定、损坏或 schema 不兼容，TUI 应显示错误并继续重试，不应修改/修复数据库。
- 自动发送前需要在界面明确显示当前监控的 home 和配置，避免误监控另一套 Codex 数据。
- 默认 dry-run 可作为首次验证模式；切换到 ON 后才真正发送。

## 10. 验收标准

第一版完成后应满足：

1. 启动 TUI 后能持续显示所有配置数据库中最新 turn 为 `inProgress` 的会话。
2. 能显示最新容量错误及其 thread/turn ID。
3. 在满足 grace period、错误新鲜度、单 thread cooldown 和全局上限后，自动执行一次 `codex queue --thread ... --message 继续`。
4. 同一失败 turn 不会因为轮询而重复发送。
5. queue 成功/失败、限流等待和后续恢复都能在 TUI 中看见。
6. TUI 重启后，发送去重和频率状态仍然有效。
7. 支持 dry-run、暂停自动发送和优雅退出。
8. 能明确区分“活跃 turn”“容量错误候选”和“历史保存会话”。
9. 监控多个 Codex home 时，每个 thread 使用正确的 `CODEX_HOME`。

## 11. 尚待确认的问题

- 默认监控范围是只监控 `~/.codex`，还是启动时自动发现 `~/.codex-sub` 等目录？
- “活跃”的错误窗口默认取 30 分钟还是 1 小时？
- 全局最高频率的默认值是多少？建议先用每分钟 5 次。
- 单会话 cooldown 默认取 5 分钟是否合适？
- queue 成功后，如果仍没有新 turn，是否需要在 TUI 中提示人工检查，而不是继续自动重发？
- 是否需要系统通知（macOS notification）或只在 TUI 中显示？
- 是否要支持切换备用模型；当前明确需求只有发送“继续”，不自动改模型。

## 12. ChatGPT macOS App 会话调研

### 12.1 先区分两种“App 会话”

ChatGPT macOS App 顶部可以进入不同产品视图。需要区分：

1. **ChatGPT App 里的 Codex 会话**：使用 Codex、项目目录、终端和 Agent 工作流的会话。
2. **普通 ChatGPT/Work 对话**：普通聊天或 Work 聊天，不一定启动 Codex agent，也不一定有本地 Codex thread。

这两类会话不能用同一种方式监控，也不能假设都有 `codex queue` 入口。

### 12.2 ChatGPT App 里的 Codex 会话：可以纳入

本机实测发现，正在运行的 ChatGPT macOS App 会启动如下 Codex app-server：

```text
/Applications/ChatGPT.app/Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex app-server ...
```

通过进程打开的文件可以确认，该 app-server 实际使用了默认 Codex home 中的数据库：

```text
~/.codex/state_5.sqlite
~/.codex/thread_history_1.sqlite
~/.codex/queue_1.sqlite
~/.codex/logs_2.sqlite
```

因此，ChatGPT App 中的 Codex 会话和 CLI/IDE 中的 Codex 会话会汇入同一个本地 thread 状态系统。现有的 Go TUI 不需要通过截图、窗口抓取或模拟点击来读取这类会话，直接读取已有 SQLite 状态即可。

在本机 `state_5.sqlite` 中观察到：

- `threads` 表包含 App 创建的 Codex thread。
- 有 thread 的 `originator` 为 `Codex Desktop`，可用于界面来源标识和筛选。
- 这些 thread 的 ID 可以与 `thread_history_1.sqlite.thread_turns.thread_id` 关联。
- 在 App 创建的 thread 中也实际出现过 `Selected model is at capacity...`，说明容量错误检测逻辑同样适用。

当前可确认的结论：

> ChatGPT macOS App 中“Codex 视图”创建的会话，可以纳入本项目的监控和自动 queue 范围。

读取路径的证据已经确认；真正执行 queue 前仍应做一次端到端验证：在一个可丢弃的 App Codex 会话上确认 `codex queue` 能被当前 App app-server 接收，并观察该会话是否产生新的 turn。若用户同时运行多个 app-server，需要在实现阶段增加 daemon/home 选择和连接失败提示。

自动发送时仍应通过该 thread 所属 Codex home 的 queue 机制处理。默认情况下使用 `~/.codex` 即可；如果未来 App 或不同账户配置产生独立 Codex home，应把 home 作为 thread 来源的一部分，而不能只用 thread ID 去重。

### 12.3 `state_5.sqlite` 对 TUI 的补充价值

`state_5.sqlite` 的 `threads` 表比 `thread_turns` 更适合展示会话列表，包含：

- `id`
- `title`
- `source`
- `originator`
- `model`
- `cwd`
- `created_at` / `updated_at`
- `archived`
- `preview` / `first_user_message`

因此建议 TUI 的数据层从两个 SQLite 数据库联合读取：

```text
state_5.sqlite.threads
        JOIN
thread_history_1.sqlite.thread_turns
        ON threads.id = thread_turns.thread_id
```

推荐用途：

- `state_5.sqlite`：会话标题、来源、模型、工作目录、更新时间、是否归档。
- `thread_history_1.sqlite`：最新 turn 状态、错误 JSON、开始/完成时间。
- `queue_1.sqlite`：只作为诊断/确认 queue 是否已经排入的辅助数据，不直接写入。
- `logs_2.sqlite`：补充诊断日志，不作为唯一状态来源。

### 12.4 普通 ChatGPT/Work 对话：目前不能纳入同一套自动恢复

官方产品说明把 Codex 视图和 ChatGPT history 分开；普通 ChatGPT 对话主要是账户云端聊天记录。macOS App 的本地目录中可以看到 Chromium/Electron 风格的缓存、Session Storage、IndexedDB/浏览器配置等文件，但这些属于应用实现细节，不是稳定的公开会话数据库接口。

目前没有找到一个可供本地 Go 程序可靠调用的“列出 ChatGPT App 正在生成的普通对话”或“向普通 ChatGPT 对话排队发送消息”的公开 CLI/API。尤其是：

- 普通 ChatGPT 对话没有可直接套用的 `codex queue --thread ...`。
- 从缓存、IndexedDB 或渲染器内存中解析聊天内容，版本升级后容易失效。
- 通过模拟点击/键盘输入发送“继续”会依赖窗口焦点和 UI，存在误发、竞态和权限问题。
- 普通 ChatGPT/Work 对话的云端状态与本地 Codex SQLite thread 状态不是同一个状态机。

因此第一版明确边界：

> 纳入 ChatGPT macOS App 的 Codex 会话；不纳入普通 ChatGPT/Work 对话。

如果未来确实需要普通 ChatGPT 对话监控，应另做独立方案，至少需要明确的官方会话 API、桌面自动化授权和发送接口，不能把读取本地缓存当作稳定实现。

### 12.5 对整体架构的影响

TUI 的来源模型建议改成：

```text
Codex CLI / IDE / ChatGPT App Codex
            |
            v
       同一套 ~/.codex 数据库
            |
            v
  state_5 + thread_history_1 + logs/queue 辅助信息
            |
            v
       Go TUI 统一展示和恢复
```

界面建议新增两列：

- `来源`：CLI、VS Code、Codex Desktop、exec 等。
- `Codex home`：该 thread 对应的本地数据目录。

自动恢复白名单也建议可配置：

```toml
allowed_origins = ["cli", "vscode", "Codex Desktop"]
```

默认可以全部纳入，但保留按来源过滤的能力，便于用户只监控 ChatGPT App Codex、只监控 CLI，或排除批处理 `exec` 会话。

### 12.6 新增验收标准

在原有验收标准基础上，加入：

1. ChatGPT App 打开的 Codex 会话能在 TUI 中出现。
2. TUI 能显示该会话来源为 `Codex Desktop` 或其他可识别 originator。
3. ChatGPT App Codex 会话出现容量错误时，能按同样规则进入限流和自动恢复流程。
4. CLI、IDE、ChatGPT App Codex 的同一 thread 不重复展示、不重复 queue。
5. 普通 ChatGPT/Work 对话明确标记为“不支持自动恢复”，不尝试解析缓存或模拟点击。
